## 三、回流规则（R7）

1. **用户生成后回填**：每个案例的「回流记录」段等真实结果——成/废标签 + 废片原因字典归类（`drift/limb/clipping/rhythm/framing/face/compliance/other`）+ 回退记录
2. **降权触发**：同废片原因 ≥3 例 → 舞句级登记 `../l3-moves/README.md`；模式级废片率 >50%（同模式 ≥4 例中 ≥2 废）→ 升级「禁用」并回写 `../degradation-log.md`
3. **A/B 基线**：CASE-03 vs CASE-10 是同输入（同窗同 BPM）的逐镜 vs 单次对照——废片率与锚点落位精度是两个模式的判定指标；CASE-06/07 的假设值路径等用户补音频后转实测路径再比
4. **小样本纪律**：<20 例的对比结论一律标注「定性参考」

### 本地 H3 无头运行方法（CASE-01 v1 实证，2026-10-24）

1. **模板来源**：本机一次真实 H3 执行的 API 快照 = 输出 mp4 内嵌的 prompt 图（VHS `save_metadata`）——`scripts/extract_h3_snapshot.py` 从 `output/MiniMaxH3/*.mp4` 提取 50 节点双通图存为 `scripts/h3_snapshot.json`（history 为空时的备选源）
2. **运行**：`scripts/run_case01.py`——6 镜顺序提交（VRAM 安全）+ 轮询 + 落盘，进度写 `assets/run_status.json`；实测约 2.7 分钟/镜
3. **装配**：`scripts/assemble_case01.py`——按故事板时长 trim 回切点（帧网格固有误差 ≤21ms）+ scale-to-cover 裁 1080×1920 + 窗口原曲混音（卡点声轨保证）
4. **音频参考接线**（v1 核心）：LoadAudio → `drive_audio`/`final_audio` + `audio_mode=lock_source` + `add_source_as_reference=True`；每镜音乐切片样本级切割后进 ComfyUI `input/`
5. **QA 回流**：逐镜抽帧核验五特写 + 全帧逐帧扫描（禁输入 seek 抽帧，伪影会误报，见 DG-016）

### 首帧构图锚点链（CASE-01 v2 实证，2026-10-24）

1. **问题**：纯 Ref2VA 时 H3 忽略文字景别指令（DG-015）——特写/中景镜被生成成默认正面全身构图
2. **修复**：Hybrid 路线（`task_type="Hybrid"`）+ `first_frame` 槽位喂构图锚点图 → **帧 0 精确命中**（④过肩特写、⑤纯侧大腿到靴均验证）
3. **锚点图生产**（`scripts/make_anchor.py`）：Qwen-Image-Edit-2511 + Multiple-angles LoRA 按运镜指令编辑角色参考图；生成失败/伪影时用数值化裁切兜底（numpy 主体 mask 定位头部/躯干 bbox → ffmpeg crop 832×1472），构图精确且零生成风险
4. **残留限制**：H3 仍在镜内 ~1–2s 漂回默认正面全身构图（DG-017）→ **QA 查 1 必须逐镜多帧抽检（帧 0/中/末），不能只查首帧**；特写镜时长尽量压短
5. **服务端稳定性**：ComfyUI 挂起时（`/system_stats` 500、队列卡死）先杀进程重启（`python_embeded/python.exe main.py`）+ 小任务探活，再提交正式任务

## 四、基线对比：M1 手写稿 vs M4 实测案例（量化）

M1 样例 #01 用**假设 96 BPM**（切点 0/2.5/5/7.5/10/12.5/15s，假设 drop@6.0s）；M4 CASE-01 用**实测 95.5 BPM**（同源窗口，切点 0.04/2.56/5.09/7.61/10.14/12.66/15s，实测 drop@7.06s）：

| 切点 | M1 假设 | M4 实测 | 漂移 |
|---|---|---|---|
| 1 | 2.50s | 2.56s | +60ms |
| 2 | 5.00s | 5.09s | **+90ms（超 ±80ms）** |
| 3 | 7.50s | 7.61s | **+110ms（超）** |
| 4 | 10.00s | 10.14s | **+140ms（超）** |
| 5 | 12.50s | 12.66s | **+160ms（超）** |

**结论**：仅 0.5 BPM 的假设误差（96 vs 95.5）在 15s 上累积到 160ms，切点 2–5 全部超出宪法容差——**「假设节拍」在 15s 尺度上不可用**，这就是 R1 实测链路存在的理由。另外假设 drop@6.0s 与实测 7.06s 差 1.06s：若实测 drop 晚于镜 4 起点（7.61s），③爆点必须后移，假设值无法预知这种位移。

## 五、M4 建设中抓出并修复的问题（回链到工具）

1. **段落检测百分位法系统性误报（beat_tracker.py 已修）**：35/65 百分位在「高能平台占多数」的曲目上两个阈值都落进平台内部——实测三曲全误报（Ukulele 真 drop@20s 报 47.16s；Lowride 无 drop 报 163.63s；快闪真入口@9s 兜底报 27.81s）。改为相对 90 分位稳健峰值的固定比例阈值（高能 >72% / 低能 <40%），三曲结构与 RMS 地面真值一致。M3 校准档案已发勘误。
2. **ffmpeg seek 在剪映 m4a 上 ~20s 偏差（新增 trim_window.py 绕过）**：`-ss` 输入/输出两种模式落点都与全解码时间线不一致（实测 RMS 对不上）。窗口裁切改为「全解码 → 样本切片 → 编码 WAV」，与 beat_tracker 共用时间线。
3. **短窗段落检测尺度硬编码（beat_tracker.py 已修）**：min_len=8s 吞掉 6s 窗的全部段落、也吞 15s 窗的 intro 段 → 被迫走兜底。改为 <30s 窗口自适应（平滑 2s / 最短段 3s + 首段并入规则仅整曲模式）。
4. **6s 3 镜网格实为「=120.0 整点」窄带（规范已修正）**：实测 120.25 BPM 差 3.3ms 即违宪（1 bar=1.9967s < 2.0s）。速查表「≈120 可 3 镜」→「=120.0±0.1」；6s 版默认形态是 2 镜。
5. **短窗 downbeat 相位不稳定（已知限制，拍吸附兜底）**：CASE-03 窗内相位 1.80s vs 全曲相位 0（差约 3 拍）→ 切点改拍吸附（相位无关）。
